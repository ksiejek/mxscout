# The architecture (C4, adapted to Mendix)

A picture of the application in the levels of the C4 model, adapted to Mendix.
In the documentation it has its own page, **Architecture**: the context and the runtime
you draw, said to be an agent's, beside how the modules depend on one another
and which user roles reach which module — both read from the model.

| Level | What it shows | Who writes it |
|---|---|---|
| 1 · Context | Who uses the application, and which systems send it data or are called by it | you, in `c4.context` |
| 2 · Containers | What the application runs as. In Mendix nearly all of it is **one runtime**, so the containers are its roles — the client, published services, background work (scheduled events, task queues), outgoing connectors — and where the data lives | you, in `c4.containers` |
| 3 · Modules | How the modules depend on one another | **MxScout reads it from the model.** Do not write it |
| 4 · Code | The flows and the domain model | the documentation itself |

## What you have to go on

- **The pack's header:** the user roles (the people), the scheduled events, the
  published services (what sends data in), and what it leaves out.
- **Each module's notes**, which you wrote first: their *Integrations* and
  *Security* sections are where the systems around the application are.
- **Hosting, the database, file storage, the number of instances, who
  provides single sign-on** are not in the model. Draw what is known, and put
  the rest in `open` as a sentence each. Never draw a system you cannot name
  from the model.

## The shape

A diagram is `nodes` and `links`.

```json
"c4": {
  "context": {
    "nodes": [
      { "id": "clerks", "name": "Clerks", "note": "confirm orders", "kind": "person", "group": "People" },
      { "id": "app", "name": "Sales", "note": "Mendix application", "kind": "app" },
      { "id": "erp", "name": "ERP", "note": "published REST, Basic", "kind": "system", "group": "Systems that send data" }
    ],
    "links": [
      { "from": "clerks", "to": "app", "label": "browser" },
      { "from": "erp", "to": "app", "label": "orders" }
    ]
  },
  "containers": { "nodes": [ … ], "links": [ … ] },
  "open": ["Where the application is hosted, and which database it uses, cannot be told from the model."]
}
```

- `id`: letters, digits, `_` and `-`, unique in the diagram. `name`: what is
  written on the box. `note`: a few words under it — a role, a protocol.
- `kind`: `person` (a group of users), `app` (the application), `system` (an
  external system), `store` (a database, file storage), `part` (a role of the
  runtime, at level 2). Anything else is drawn as a system.
- `group`: boxes drawn together inside a dashed frame with this name.
- `links`: `from` and `to` are node ids; a link to a node that is not there is
  dropped. `label`: one or two words for what flows.
- MxScout lays the pictures out by the direction of the links, so write them
  the way the data or the request goes: people → application → systems it
  calls. The context's groups go around the application (see below); in the
  containers, people and the systems that call in stand on the left, the
  `part`s inside one frame for the runtime, and stores and the systems the
  parts call on the right.

## How much

Everything the application really talks to and runs as, nothing left out: a
large application has a dozen systems around it, and each one belongs in the
picture. Keep it readable by grouping — systems of the same kind in one group,
people by what they do — rather than by dropping any. MxScout keeps up to 100
nodes and 250 links in a diagram. Labels short. A link between two
groups is drawn once, not once per node.

The context's groups are also drawn on the documentation's overview, around the
application, by the direction of their links: people, and systems that only
send to it, on the left; systems it only calls on the right; a group with links
both ways above it. So keep the context to **five groups at most**, and put
systems in a group by which way they talk to the application, not only by what
they are.
